Lesson 5

Errors in async code

How a server catches a failure, picks the right status code, and keeps running for the next visitor.

The idea

Things go wrong on a server. A file is missing, some text is not valid JSON, or a promise is rejected instead of settling with an answer. One server answers every visitor, so one visitor's bad request must not take the site down for everyone else.

Inside an async function, a rejected promise that you await throws, just like an error in ordinary code. So you can handle it with try and catch: put the risky line in try, and decide in catch what the visitor should get back.

When you do not catch an error, Express 5 catches it for you. If an async route handler throws, Express sends the error to the server's error-handling middleware, which turns it into a plain 500 answer.

The demo on this page fails on purpose, in a different way for each type in the query string.

The code

This is the code behind the demo, copied from this site's own source. First, the fail handler. Each if handles one type. The first three catch their own error. uncaught does not.

demos.js 
// The kinds of error /demo/fail can show.
const FAIL_TYPES = ['reject', 'missing-file', 'bad-json', 'uncaught'];

// A file that does not exist, for the missing-file and uncaught demos.
const MISSING_FILE = path.join(PROJECT_DIR, 'no-such-file.txt');

// GET /demo/fail?type=: errors on purpose, and how the server handles them.
export async function fail(req, res) {
  const { type } = req.query;

  if (type === 'reject') {
    try {
      await Promise.reject(new Error('This promise was rejected on purpose.'));
    } catch (error) {
      console.error('fail reject:', error.message);
      return res.status(500).json({ type, caught: true, error: error.message });
    }
  }

  if (type === 'missing-file') {
    try {
      await readFile(MISSING_FILE, 'utf8');
    } catch (error) {
      // error.message names the full path on this computer, so it stays here.
      console.error('fail missing-file:', error.message);
      return res.status(404).json({ type, caught: true, code: error.code });
    }
  }

  if (type === 'bad-json') {
    try {
      JSON.parse('{"name": "Node"');
    } catch (error) {
      console.error('fail bad-json:', error.message);
      return res.status(500).json({ type, caught: true, error: error.message });
    }
  }

  if (type === 'uncaught') {
    // No try/catch. Express 5 sends the rejected promise to the error handler.
    await readFile(MISSING_FILE, 'utf8');
  }

  res.status(400).json({ error: 'type must be one of validTypes.', validTypes: FAIL_TYPES });
}

Each catch does two jobs. console.error writes the details in the server's terminal, for you. The return res.status(...).json(...) sends a short answer to the browser, for the visitor, and return stops the function there. A type that matches no if reaches the last line and gets a 400.

In server.js, one line connects the path to the handler:

server.js 
app.get('/demo/fail', fail);

The error-handling middleware is the last thing in server.js before app.listen. Express knows it handles errors because its function has four parameters, with the error first.

server.js 
// The error handler has four parameters, so Express sends every error here.
// The details go to the terminal, never to the browser.
app.use((error, req, res, next) => {
  console.error(error);
  if (res.headersSent) return next(error);
  res.status(500).json({ error: 'Something went wrong on the server.' });
});

res.headersSent is true if an answer had already started going out before the error happened. Then it is too late to send a different one, so next(error) hands the error to Express's own built-in handler.

What just happened

      
Every button got an answer, and none of them stopped the server. Each
      one came back with a different status code or body:

      
    
        
  • reject: HTTP 500 Internal Server Error.
        await turned the rejected promise into a thrown error, and
        catch caught it. The body says
        "caught": true and repeats the error's message,
        "This promise was rejected on purpose."
    • 
        
  • missing file: HTTP 404 Not Found. Reading
        no-such-file.txt failed with the code
        "ENOENT", which is Node's code for "no such file or
        directory". The handler chose 404 because the thing asked for is not
        there. The body has the code but not the message, because the message
        includes the file's full path on the server's disk. The path appears
        only in the server's terminal.
    • 
        
  • bad JSON: HTTP 500 Internal Server Error.
        JSON.parse threw because the text is missing its closing
        }. The message says where it gave up: "Expected ','
        or '}' after property value in JSON at position 15 (line 1 column
        16)". JSON.parse is not async at all, and
        try/catch handles it the same way.
    • 
        
  • uncaught: HTTP 500 Internal Server Error. This
        time there is no "caught" and no "type". The
        body is only "Something went wrong on the server.", the
        message from the error-handling middleware. The
        fail handler never sent anything. Its
        await threw, and Express 5 passed the error to the
        middleware. In the terminal, the middleware's
        console.error printed the full error, path and all. The
        browser got none of it.
    • 
        
  • type=oops: HTTP 400 Bad Request. Nothing went
        wrong on the server. The request asked for something that does not
        exist, so the answer says what was wrong and lists the four
        validTypes.
    • 
      

      
The lesson: catch errors where you know what they mean, so you can
      send the right status code. 404 means "not here" and 400 means "bad
      request". For everything you did not expect, the error-handling
      middleware sends a safe 500, keeps the details in the terminal, and the
      server goes on answering the next request.
