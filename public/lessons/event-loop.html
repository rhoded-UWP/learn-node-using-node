Lesson 3

The event loop

Why Node.js runs your code in an order you might not expect, and how to predict that order.

The idea

Node.js runs your JavaScript on one thread. It does one thing at a time. When your code asks for something to happen later, Node.js does not stop and wait. It saves your callback in a queue, finishes the code it is running now, and comes back for the callback afterward. The event loop is the part of Node.js that keeps going back to those queues.

There is more than one queue, and Node.js empties them in a fixed order. This lesson uses five ways to run code:

  • Synchronous code: plain lines that run right now, top to bottom.
  • process.nextTick: run this as soon as the current code finishes.
  • A promise's .then: run this once the promise is settled. Promise.resolve() is already settled.
  • setImmediate: run this on the event loop's next check for immediate callbacks.
  • setTimeout with 0 ms: run this on the event loop's next check for timers, once 0 ms have passed.

The demo schedules all five in one request and writes down the order they really run in.

The code

This is the handler that answers the demo, copied from this site's own source. Read the order the lines are written in, then guess the order they run in.

demos.js 
// GET /demo/order: five ways to run code, and the order Node.js runs them in.
// They are scheduled in this order on purpose, so you can compare.
export function order(req, res) {
  const labels = [];

  // Each one records its label when it runs. The fifth one sends the answer.
  function record(label) {
    labels.push(label);
    if (labels.length === 5) res.status(200).json({ order: labels });
  }

  setTimeout(() => record('setTimeout 0 ms'), 0);
  setImmediate(() => record('setImmediate'));
  Promise.resolve().then(() => record('promise .then'));
  process.nextTick(() => record('process.nextTick'));
  record('synchronous code');
}

The response cannot go out as soon as the function ends, because four labels are still waiting in queues. So record counts them, and whichever callback runs fifth sends the JSON. In server.js, one line connects the path to the handler:

server.js 
app.get('/demo/order', order);

What just happened

      
The server answered HTTP 200 OK with this order,
      which is almost the reverse of the order the code was written in:

      
    
        
  1. "synchronous code" ran first, even though it is the
        last line. Everything else was only scheduled. Node.js always
        finishes the code it is running before it looks at any queue.
    2. 
        
  2. "process.nextTick" came next. Node.js runs the
        nextTick queue the moment the current code finishes.
    3. 
        
  3. "promise .then" was third. Promise callbacks run right
        after the nextTick queue is empty, still before the event
        loop moves on.
    4. 
        
  4. "setImmediate" was fourth.
    5. 
        
  5. "setTimeout 0 ms" was last, even though it was
        scheduled first and asked for no delay at all.
    6. 
      

      
Why did setImmediate beat a 0 ms timer? This handler
      only runs because a request arrived over the network. The event loop
      was busy handling that input when it called the handler. After
      handling input, its next stop is the immediate callbacks. Timers come
      later, on its next trip around the loop. Run the demo a few more times:
      the order is the same every time.

      
The lesson for a server: "0 ms" does not mean "now". It means "when
      the event loop gets to timers". Code that is still running always goes
      first, and every queued callback waits until it is done.
