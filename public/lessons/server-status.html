Lesson 6

Server status

A Node.js server is one program that keeps running, so it can remember things between requests. With a database, it can remember them even after it restarts.

The idea

JavaScript in a browser starts over every time you load a page. This server is different. It starts once and then keeps running, answering request after request. A variable made when it starts stays in memory for as long as the server runs.

That lets the server keep a count. A small piece of middleware, a function that Express runs on a request before any route sees it, adds 1 to a counter and then calls next() to pass the request along.

A count in memory is lost when the server stops. So the same middleware also adds 1 to a row in a Postgres database, which keeps its data after the server restarts. The page shows both counts side by side, so you can compare them.

Node.js can also report on itself through the global process object: which version of Node is running, on which operating system, how long it has been running, and how much memory it is using.

The code

This is the code behind the demo, copied from this site's own source. First, the counter in memory, the middleware that counts requests, and the status handler:

demos.js 
// When the server started. This line runs once, when server.js imports demos.js.
const startedAt = new Date();

// How many requests the server has answered since it started. It lives in
// memory only, so it goes back to 0 every time the server restarts.
let requestsSinceStart = 0;

// Middleware: count requests. server.js runs it before express.static, so it
// counts every request: pages, styles, scripts, icons, and demos.
// It counts twice: once in memory, and once in the database's 'requests' row.
export async function countRequests(req, res, next) {
  requestsSinceStart += 1;

  // res.locals keeps values for this one request, so status can read them.
  res.locals.requestsAllTime = null;
  try {
    const result = await query(
      'UPDATE site_stats SET value = value + 1 WHERE name = $1 RETURNING value',
      ['requests'],
    );
    // pg returns a BIGINT as text, so turn it into a number.
    res.locals.requestsAllTime = Number(result.rows[0].value);
  } catch (error) {
    // No database: log it, and still serve the page.
    console.error('Could not count the request in the database:', error.message);
  }
  next();
}

// GET /demo/status: facts about this running server, right now.
export function status(req, res) {
  const memoryBytes = process.memoryUsage().rss;
  const { requestsAllTime } = res.locals;
  res.status(200).json({
    nodeVersion: process.version,
    platform: process.platform,
    uptimeSeconds: Math.round(process.uptime()),
    requestsSinceStart,
    requestsAllTime,
    database: requestsAllTime === null ? 'not connected' : 'connected',
    memoryUsedMB: Math.round(memoryBytes / 1024 / 1024),
    startedAt: startedAt.toISOString(),
  });
}

countRequests is now async. It uses await to wait for the database to add 1 and send back the new total (that is what RETURNING value asks for). Only then does it call next(). The $1 in the SQL is filled in from the array after it, ['requests'], so a value is never pasted into the SQL text.

If the database fails, catch writes the reason in the terminal and next() still runs, so the page is still served. res.locals is an object Express gives each request. The middleware leaves the all-time count there, and status reads it from there. When it is still null, status reports the database as not connected.

query comes from db.js, the one file that talks to the database:

demos.js 
import { query } from './db.js';

In server.js, the order matters. Express runs app.use middleware in the order it is written, so countRequests comes first, before the 405 check and before express.static. That way it sees every request, even ones that never reach a route.

server.js 
// Count every request, before anything else can answer it.
app.use(countRequests);

Further down, one line connects the demo's path to the handler:

server.js 
app.get('/demo/status', status);

Comparing the two counters

      
Click the button twice in a row, and both counters
      go up by exactly 1. The button sends one request, and
      countRequests adds 1 to each counter.

      
Reload the page, and both go up by more than 1. One page load is
      several requests. The browser first asks for the page,
      /lessons/server-status. Then it reads the HTML and asks the
      server for each file it needs: /styles.css,
      /js/try-it.js, and usually /favicon.svg, the
      tab icon. Every one of those requests passes through
      countRequests before express.static sends the
      file. When this server was tested, loading a page with its three files
      and then asking for the status moved both counters up by 5: 4 for the
      page load and 1 for the status request. The server's terminal shows one
      line per request.

      
The two counters differ after a restart. When this
      server was tested, the counts were equal before it stopped. Right after
      it started again, the status showed "requestsSinceStart": 2
      but "requestsAllTime": 11. The variable in memory started
      over at 0. The row in the database kept its value and went on counting
      from there. On a site that has been running for a while,
      requestsAllTime is usually much bigger.

      
When the database cannot be reached, the server still answers. When
      this server was tested with no database, the page still loaded with HTTP
      200, and the status showed "requestsAllTime": null and
      "database": "not connected". The memory counter kept
      working, and the terminal printed why the database count failed.

      
The lesson: memory is fast but forgets when the program stops. A
      database remembers. A real site keeps anything that must last, like
      users, orders, and counts, in a database.
